## 一、设计目标与三个检验

### 1.1 设计目标

| # | 目标 | 说明 |
| --- | --- | --- |
| G1 | **首页承担「判断」职责** | 首屏用自然语言说出「今天最该做什么」，并直接给动作。首页从「原料陈列台」变为「会做判断的同事」。 |
| G2 | **到达动作只需一句话 / 一次点击** | 主入口按「你要做什么」组织（意图流 + ⌘K），不再按「去哪个系统」组织；应用宫格降为次级入口。 |
| G3 | **视觉权重随紧迫度衰减** | 以时间紧迫度为组织主轴，纵向流式行项目（Notion database/row 气质）；紧急项大而醒目，知悉项小而克制。 |

> **三个目标正交**：G1 解决「有没有观点」，G2 解决「路径长度」，G3 解决「视觉落点」。互不重叠、可分别验收。

### 1.2 三个检验（引用简报，并量化为可走查/可埋点的验收标准）

| 检验 | 简报原文口径 | 本规格的落地方式 | 可验证标准 |
| --- | --- | --- | --- |
| **三秒检验** | 打开首页 3 秒内能说出「今天最该做的第一件事」 | 首屏左上角第一块内容是「今日简报」卡，其第一句陈述句即「最要紧的一件事 + 时限」；PC 中栏流的第一行是该事的行项目（含倒计时与「立即处理」）；移动端首屏紧接简报就是「最要紧的一件事」大卡 | ① 简报卡在首屏视口内（PC 1440×900 / 移动 375×667）**无需滚动即可见**；② 走查 5 名测试用户，3 秒内说出第一件事的正确率 ≥ 4/5；③ 埋点：首屏曝光至点击「立即处理」的中位时长 < 15s |
| **一句话检验** | 用一句话（而非点击 3 层菜单）到达目标动作 | ① PC 主入口 = **⌘K 命令栏**（输入「发起请假」直达预填表单）；② 意图流 = **一次点击**直达（站内直接拉起表单 / 外部带 SSO 直达目标页）；③ 移动端主入口 = AI 对话入口（拇指可达） | 从首页到达目标动作的**点击数 ≤ 1**；⌘K 与意图流覆盖简报方向里列的全部 7 个意图动作（发起审批 / 提个报销 / 我要请假 / 查我的合同 / 找人 / 看本月数据 / 催个办），全部一跳可达 |
| **权重检验** | 最紧急的事与最不重要的事视觉权重明显不同 | 时间轴流按紧迫度分三组，行高/字号/色条/操作按钮形态**逐级衰减**（见第三章 3.3.3 权重表）：今天必须做（72px / 16px 标题 / 3px 品牌红色条 / 实心主按钮）→ 本周待办（56px / 15px / 3px 暖橙 / 文字按钮）→ 知悉即可（44px / 14px / 细线 / 无按钮） | 「今天必须做」行高 ≥ 「知悉即可」行高 × 1.5；两者不用同等大小的卡片容器；走查确认**首屏不存在「一样大的方块阵列」** |

### 1.3 三个目标与页面区块的对应

| 目标 | PC 承载区块 | 移动端承载区块 |
| --- | --- | --- |
| G1 判断 | 今日简报（左栏 B1） | 精简简报（B1）+ 最要紧的一件事大卡（B2） |
| G2 路径 | 意图流（左栏 B2）+ ⌘K 命令栏（B6）+ AI 助手浮层（B7） | AI 对话入口（B1）+ AI 对话抽屉（B7）+ 意图胶囊（B4）+ 底部行动栏（B5） |
| G3 权重 | 时间轴流（中栏 B3） | 最要紧的一件事大卡（B2）+ 其余待办流（B3） |

## 二、信息架构重构对照表

| 维度 | 现有（要打破） | 重构后 | 打破的理由 |
| --- | --- | --- | --- |
| **首屏核心** | 红色渐变问候横幅（`greet-card`）+ 24 栅格卡片大盘平铺 | **AI 今日简报**：问候 + 自然语言判断 + 优先级 + 行动按钮（PC 左栏首块 / 移动首屏第一句） | 横幅只复述计数（「你有 6 条待办」），把判断推给用户；简报直接给结论与动作 |
| **主入口** | 应用宫格 8 图标（先想「去哪个系统」） | **意图流**（PC 左栏，7 个意图项 + 「全部应用 ›」）/ **⌘K 命令栏**（PC 主入口）/ **AI 对话入口**（移动主入口）；宫格降级为次级入口 | 用户脑中的问题是「我要请假」而非「我要打开 OA」；认知成本从入口后移到意图层，且意图层能覆盖 80% 高频动作 |
| **组织主轴** | 卡片类型（待办卡 / 应用卡 / 消息卡 / 数据卡） | **时间紧迫度**：今天必须做（品牌红）→ 本周待办（暖橙）→ 知悉即可（暖灰），纵向流式行项目 | 以「类型」组织时，紧急与不紧急被切成不同容器，无法横向比较；以「紧迫度」组织，眼睛一眼扫到红色段 |
| **视觉权重** | 所有卡片同尺寸同权重（grid 6/8/12/16/24 只调宽度）；紧急与可有可无一样大 | **权重随紧迫度衰减**（行高 / 字号 / 色条 / 操作形态四维同步衰减） | 均匀栅格让眼睛没有落点；权重差异本身就是「判断」的可视化 |
| **容器形态** | 卡片 = 方块容器（`card` + `card-head` + body） | **流式行项目**（`UrgencyRow`，Notion database/row 气质）；页面骨架为纵向流 + 栏 | 「卡片墙」天然暗示「平等罗列」；行项目天然支持「排序 + 权重 + 行内操作」 |
| **应用入口位置** | 首屏第 2 块（与待办卡并列） | PC：右栏底部「全部应用」次级入口 + ⌘K 可搜应用；移动：底部收纳入口（B6）。**仍保留、不再占首屏** | 常用应用是「兜底入口」而非「主路径」，占首屏即抢占最高认知位 |
| **消息 / 公告** | 独立「消息 / 公告」卡片 | 并入右栏**关注与动态**（B4）流式行（含置顶公告、系统维护通知、审批结果）；**不进时间轴流**（见 §3.3.3 分工说明） | 公告/消息是「阅读类」信息，动作语义与「待办」不同；混入时间轴会让「时间轴 = 待办」的语义失焦 |
| **数据指标卡** | 首屏「数据指标（V1.5 占位）」8 栅格 | 移出首屏 → 右栏「本月速览」（B5），PC 默认可见但权重最低；移动端收纳入口 | 占位卡片压在首屏是「为未来功能预留黄金位」，属反产品设计 |
| **移动端结构** | 渐变问候卡 → 金刚区 4 图标 → 紧急待办列表 → 常用应用宫格（2018 企业门户范式） | 精简问候 + AI 简报（1–2 句）→ **最要紧的一件事大卡（首屏必见）** → 其余待办紧凑流 → 意图胶囊横滚 → 底部固定行动栏 + 应用收纳 | 移动端不该是 PC 缩小版；顶部大横幅吃掉首屏，用户看不到最要紧的事；金刚区 = 缩小版宫格，同样犯「导航优先」的错 |
| **交互特色** | 鼠标点击为主，无键盘能力 | PC：⌘K（键盘优先）、悬浮预览、编辑模式拖拽；移动：下拉唤起 AI、左右滑处理待办、底部固定行动栏 | 交互方式要匹配场景（PC = 键盘 + 多任务；移动 = 拇指 + 即时） |

## 三、PC 首页设计（`prototype/home-v2.html`）

### 3.1 页面骨架与栅格

| 项 | 规格 |
| --- | --- |
| 路由 | `/home`（原型 `home-v2.html`）；页面 ID `UI-A1-01`（重构版，编号不变） |
| 顶栏 | 56px sticky，毛玻璃（复用样稿 `.topbar`：`rgba(255,255,255,.72)` + `backdrop-filter` + 1px 下边框） |
| 内容区 | `max-width 1440px` 居中，左右 `padding 24px`，栏间 `gutter 16px` |
| 三栏 | 各 `8/24` 栅格（约 453px）：**左栏**（今日简报 + 意图流）/ **中栏**（时间轴流，主区）/ **右栏**（关注与动态 + 本月速览 + 全部应用） |
| 栏内栅格 | 每个栏是**独立的 24 栅格容器**（`LayoutGrid` 递归使用）：栏内卡片默认 `grid:24`（占满栏宽、纵向堆叠） |
| 断点 | `≥1440px` 三栏；`1024–1439px` 右栏折叠为「吸底抽屉」触发条（顶栏右侧「速览」按钮），保持左 + 中双栏；`<1024px` 沿用既有「建议更大屏幕」提示，左栏 + 中栏可用 |
| 行高基线 | 4px 阶梯；卡内 padding 16px；流式行项目垂直 padding 12px |

### 3.3 各区块设计

#### 3.3.1 今日简报区（`ai-brief` · B1）

**结构（自上而下）**

| 序号 | 元素 | 规格 |
| --- | --- | --- |
| 1 | 问候行 | 「早上好，张三」+ `·` + 日期（`09-22 周二`）+ `·` 部门；16px/400，`#615d59`；时段问候沿用既有逻辑（夜深/早上/中午/下午/晚上） |
| 2 | AI 标识 | 卡片头右侧 `AI` 徽标（12px/600/字距 +0.125px，胶囊 9999px，品牌红底白字）；徽标 `title`「由 AI 根据你的待办、时限与进度生成」 |
| 3 | AI 摘要文案 | 2–4 句自然语言；每句一件；`16px/400/行高 1.5`，正文 `rgba(0,0,0,.95)`；**关键实体（合同名 / 人名 / 金额）用 600 字重**，时限用品牌红 600 |
| 4 | 优先级判断 | 用 ①② 序号 + 「今天有 N 件事要先处理」的显式判断句（N ≤ 3）；结尾一句「其余 N 件可以晚点看」 |
| 5 | 行动按钮 | 主按钮「立即处理 →」（品牌红实心，38px 高，8px 圆角）+ 次按钮「看全部」（`btn-ghost`）；主按钮跳到第 1 件事的目标页（站内 → 拉起办理 / 跳转 → 新标签 SSO） |
| 6 | 折叠项 | 行「▸ 其余 3 件（展开）」，点击展开为简报内的紧凑行列表（每条：① 序号 + 标题 + 时限），展开态不改变卡高以外的布局（卡内滚动上限 240px）。**示例口径（对齐 `MOCK.todos` 6 条）**：简报必说 3 件（① 合同审批剩余 3h ② 简历初筛已超时 2h ③ 采购审批剩余 6h），「其余 3 件」= 本周 2 件（折扣审批 / 请假审批）+ 知悉 1 件（OKR 确认） |

**交互规则**

1. 「立即处理」永远指向**简报里第 1 件事**（与中栏时间轴流第一行是同一对象，避免两处不一致）。
2. 折叠展开状态本轮不持久化（刷新回默认折叠）；若后续需要记忆，用 `sessionStorage`（与既有 `bmp_onboarded` 同策略）——**待确认**。
3. 简报**不展示原始数据条数汇总**（如「你有 6 条待办、3 条未读」），该信息由时间轴流的「今天要看的事 · N 件」与顶栏角标承担；避免两张卡说同一件事。
4. 简报卡可被用户在编辑模式隐藏（`visible:false`）——隐藏后时间轴流自然上移成为首屏，这是**渐进式采纳**路径（保守用户可退回清单范式），设计上必须保证隐藏后首页**不残缺**（见第六章空态与边界）。

#### 3.3.3 时间轴流区（`urgency-stream` · B3，主区）

**分组与权重表**

| 分组 | 判定 | 行高 | 标题字号 | 左侧色条 | 时限呈现 | 行内操作 | 附加信息 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| **今天必须做** | `urgency=2`（紧急）**或** `overdue=true` **或** `remainHours ≤ 4` | 72px | 16px/600 | 3px 品牌红 `#C8161D` | 品牌红 600 + 倒计时（「剩余 3h」/「已超时 2h」） | **实心主按钮**「立即处理」 | 金额 / 提交人 / 来源全展示 |
| **本周待办** | `remainHours ≤ 168`（7 天）且未落入上一组，**且非「知悉即可」判定** | 56px | 15px/500 | 3px 暖橙 `#dd5b00` | 暖橙 12px/600 | **文字按钮**「去处理」（hover 才现） | 仅来源 + 时限 |
| **知悉即可** | `urgency=0` **且** `remainHours > 24`（即「普通且不急着今天看」） | 44px | 14px/400 | 无（上边框 `1px solid rgba(0,0,0,.1)`） | 暖灰 `#a39e98` 12px | 无按钮（整行可点） | 单行省略，超长 `text-overflow: ellipsis` |

> **与「消息 / 公告」的分工（避免重叠）**：**公告与消息不进时间轴流**，它们只在右栏 B4「关注与动态」出现（含置顶公告、系统维护通知、审批结果）。时间轴流的「知悉即可」只放**待办性质的知悉项**（例如「目标确认 Q3 OKR 对齐」）。理由：待办需要「处理或知悉」，公告只需要「阅读」——两者的动作语义不同，混在一起会让「时间轴 = 待办」的语义失焦。

**行项目结构（`UrgencyRow`）**

```
[色条3px] [状态点 ●] [标题（1 行省略）]               [时限徽标] [操作按钮]
          [来源 · 提交人 · 时间（12px 暖灰，仅第一组展示）]
```

**交互规则**

1. **组头**为轻量文字（示例：`▎今天必须做 (3)` / `▎本周待办 (2)`，13px/600，暖灰），不使用卡片容器包裹；组与组之间用 24px 间距 + 一细分隔线，不使用不同底色（保持「一张纸上的流」）。
2. **分组可折叠**：「知悉即可」默认折叠为一行「▎知悉即可 (1) ▸ 展开」；「今天必须做」「本周待办」默认展开。
3. **行内直接操作**（`去处理` / `标记完成`）：
   - `mode=站内`（中台自有流程）→ 点击「立即处理」在当前页打开办理轻抽屉（复用 UI-WF-06 办理能力），**标记完成**可站内直接写回；
   - `mode=跳转`（外部系统）→ 点击「立即处理」新标签打开源系统处理页（带 SSO）；hover 显示次级文字按钮「标记完成（源系统回执后生效）」，点击后行变「已提交处理 → 待源系统回执」的中间态（诚实反馈，不假装已办）。
4. **行点击** = 打开详情（PC 用右侧 Drawer 640px，沿用「详情抽屉范式」），不跳整页。
5. 排序：组内按 `overdue` → `remainHours` 升序 → `urgency` 降序；已处理项即时从流中移除并 Toast（沿用 A4 口径）。
6. 流底部固定一行：「查看全部 N 条 →」（N = 待办总数，示例数据为 6）跳 `todos.html` / 审批中心。
7. **行项目渲染上限 20 条**（见第六章数据量边界）。

#### 3.3.7 编辑模式兼容设计（关键）

> **目标**：新首页的区块以**新 cardId 注册进 manifest**，沿用「`layoutTemplate` + `user_override` 深合并」「卡片注册渲染器」「栅格/显隐/排序可调、cardId 集合不可增删」三条既有机制，**不另起一套布局系统**。同时必须让三栏结构在既有 24 栅格术语下可表达。

**① 新 cardId 注册建议（`MOCK.cardManifest` 增量）**

| cardId | 名称 | minGrid（栏内） | dataApi（建议，**待确认**） | 说明 |
| --- | --- | --- | --- | --- |
| `ai-brief` | 今日简报（AI） | 24（栏内满宽） | `GET /v1/portal/brief`（建议）；依赖 AI 中台 `/ai/**`（既有网关路由 `enabled:false`） | 可隐藏（渐进采纳） |
| `intent-stream` | 意图流 | 24 | `GET /v1/portal/intents`（建议；也可前端配置 + 权限过滤，V1.0 更稳） | 隐藏后首页仍完整（可从 ⌘K 覆盖） |
| `urgency-stream` | 时间轴流 | 24 | `GET /v1/todos?groupBy=urgency&top=20`（建议在既有 `/v1/todos` 增加分组参数） | 不建议隐藏（可隐藏，但首屏会失去主区） |
| `watch-list` | 关注与动态 | 16 | `GET /v1/portal/watch`（建议） | 合并原「消息/公告」 |
| `data-metrics` | 本月速览 | 12 | `GET /v1/metrics`（既有，V1.5 完整） | 复用既有 cardId，仅改名称与默认模板位置 |
| `frequent-apps` | 全部应用（次级入口） | 12 | `GET /v1/apps/frequent`（既有） | 复用既有 cardId，降级为次级入口 |
| `notice-msg` | 消息/公告 | 16 | `GET /v1/messages/unread-count`（既有） | **保留注册**（`visible:false`），不删除 |

**硬规则：不删除任何既有 cardId（`todo-list` / `frequent-apps` / `notice-msg` / `data-metrics` / `birthday`）。** 原因：老用户的 `user_override_json` 中可能引用这些 id，删除会导致覆盖配置失配/渲染报错。新默认模板只改变它们的 `visible / order / grid`（例如 `todo-list` 在 v2 模板中 `visible:false`，因为其职责被 `urgency-stream` 取代）。

**② `layoutTemplate` 默认模板调整（新增 `version: 2` 的 `zones`，向后兼容）**

```json
{
  "version": 2,
  "zones": [
    { "zone": "left", "grid": 8, "cards": [
        { "cardId": "ai-brief",      "name": "今日简报（AI）", "grid": 24, "order": 1, "visible": true },
        { "cardId": "intent-stream", "name": "意图流",        "grid": 24, "order": 2, "visible": true } ] },
    { "zone": "center", "grid": 8, "cards": [
        { "cardId": "urgency-stream", "name": "时间轴流",     "grid": 24, "order": 1, "visible": true } ] },
    { "zone": "right", "grid": 8, "cards": [
        { "cardId": "watch-list",    "name": "关注与动态",    "grid": 24, "order": 1, "visible": true },
        { "cardId": "data-metrics",  "name": "本月速览",      "grid": 24, "order": 2, "visible": true },
        { "cardId": "frequent-apps", "name": "全部应用",      "grid": 24, "order": 3, "visible": true } ] },
    { "zone": "legacy", "grid": 0, "cards": [
        { "cardId": "todo-list",  "name": "待办卡片",   "grid": 12, "order": 90, "visible": false },
        { "cardId": "notice-msg", "name": "消息/公告",  "grid": 16, "order": 91, "visible": false },
        { "cardId": "birthday",   "name": "员工生日卡", "grid": 6,  "order": 92, "visible": false } ] }
  ]
}
```

- **`version: 1`（仅有 `cards`，无 `zones`）时渲染器仍按旧逻辑平铺**——这是给「已发布的老模板」和「UI-C-11 里存量模板」的兼容路径。
- **关键设计**：老卡片（`todo-list` / `notice-msg` / `birthday`）放在一个 `grid:0` 的 **`legacy` 区**里 `visible:false`——**而不是另立一个数组**。这样 `user_override` 的深合并仍然只需沿 `zones[].cards[]` 单一路径遍历（`cardId` 集合在 v2 模板中保持完整，用户想恢复时只需把 `todo-list` 的 `visible` 改回 `true`，无需改模板）。
- 引擎机制**零变更**：读 `template_json`（角色模板）→ 深合并 `user_override_json` → 按 `order` 排序 → 按 `grid` 排布 → 每 cardId 查 manifest 取渲染器与数据接口。`CARD_RENDERERS` 注册表新增 4 个渲染器即可（**新卡片 = 注册 manifest + 注册渲染器，零平台改造**的架构承诺不变）。

**③ `user_override` 与编辑模式如何继续可用**

| 既有能力 | 三栏下的规则 |
| --- | --- |
| 拖拽排序 | **栏内排序**（拖拽/「↑↓」交换同栏内相邻卡的 `order`）。**跨栏禁用拖拽**（bar 工具条提示「跨栏请用显隐调整」）——因为栏宽由 zone 决定，跨栏移动会使结构坍缩 |
| 显隐开关 | 每卡 `visible` 可切换；隐藏后同栏余下卡片自动上移；**所有卡都可隐藏**（含简报），但设计保证「全部隐藏」时该栏显示一条空栏提示（见第六章） |
| 栅格调整器 | 栏内可用档位 **12 / 16 / 24**（栏内为独立 24 栅格；`minGrid` 由 manifest 约束）；栏宽本身（8/8/8）**用户不可改**（属角色模板，由管理员在 UI-C-11 配置） |
| 保存 / 恢复默认 | 「保存」写 `user_override_json`（`{ cards: [{cardId, order, visible, grid}] }`，**结构不变**；`zone` 属模板层不写入 override）；「恢复默认模板」清空 override 回到 v2 角色模板 |
| 编辑模式视觉 | 沿用既有：`body.editing` + 虚线框 `outline: 2px dashed`、`card-ops`（↑↓/👁）、`grid-size-bar`；工具条文案更新为「拖拽卡片标题可在本栏内排序 · 点击按钮调整显隐与宽度 · 卡片集合不可增删（决议 #6）」 |
| 单卡失败降级 | 沿用：单卡渲染失败显示错误占位 + 「重试」，不影响其他卡（UIUX 5.3 规则 4） |
| UI-C-11 布局模板编辑器 | **需同步升级（增量需求）**：物料面板增加「三栏分组」，画布实时渲染 v2 `zones` 结构；素材来源仍是 manifest 注册表。**判定为 A1-F02 的连续演进（编辑器跟随模板协议），不是新能力** |

**④ 若引擎协议暂不允许 `version:2`（降级方案，仅在待确认项 Q1 结论为「不允许」时启用）**

- **方案 A（零扩展）**：三栏降级为「上三下二」两行结构——第一行 `ai-brief(8) + urgency-stream(8) + watch-list(8)`，第二行 `intent-stream(8) + data-metrics(8) + frequent-apps(8)`。视觉仍能通过 8/8/8 表达「并列信息」，但左栏无法堆叠两卡、中栏无法纵向贯通。**验收降级**：三秒检验仍可过（简报在左上首块）；但「中栏为主区」的表达力明显减弱。
- **结论**：推荐 `version:2`，以保住简报裁定的三栏方向。

## 五、AI 融入设计（专节）

> 三处 AI 严格对应简报第四章：**① 今日简报 ② 意图流 + 智能填单 ③ AI 对话入口 / ⌘K**。

### 5.1 今日简报的生成逻辑（产品侧描述）

**输入（判定依据，全部来自既有或建议接口，标注待确认）**

| 输入 | 来源 | 用途 |
| --- | --- | --- |
| 待办集合（标题 / 来源 / `urgency` / `remainHours` / `overdue` / 提交人 / 业务类型 / 关联金额） | `MOCK.todos` 同构数据（`GET /v1/todos`） | 排序主依据 |
| 我发起的流程实例（当前节点 / 状态 / 停留时长） | 既有 `MOCK.workflow.approvalCenter.initiated` / `instances` | 「我在等的事」与「被驳回待重提」 |
| 未读消息（分类：审批结果 / 系统通知 / 待办提醒） | 既有 `MOCK.messages` | 右栏 B4「关注与动态」+ 简报收尾句 |
| 置顶公告 | 既有 `MOCK.notices` | 右栏 B4（**不进时间轴流**，见 §3.3.3 分工说明） |
| 剩余年假 / 日历忙闲 | **待确认（Q8）**——既有 mock 无此数据 | 智能填单与「今天是否有人休假影响审批」 |

**排序优先级（可解释规则链，非黑箱；AI 只负责措辞，不负责凭空判断）**

> **主排序**：`urgency` 降序 → `remainHours` 升序（临期在前）。
> **超时项不自动霸占首位**（避免过期项长期占据首屏、把新到期项顶下去），而是「按 urgency 参与排序 + 红色『已超时』标注 + 在简报中显式提一句」——既保证被看见，也不让首页长期停留在昨天的事上。

以 `MOCK.todos`（6 条）为示例的排序结果：

| 序 | 事项 | urgency | remainHours | 落入分组 |
| --- | --- | --- | --- | --- |
| 1 | 华宇科技采购合同审批 | 2 紧急 | 3 | 今天必须做 |
| 2 | 采购审批 ¥86,000 | 2 紧急 | 6 | 今天必须做 |
| 3 | 简历初筛 ×3（**已超时 2h**） | 1 重要 | −2 | 今天必须做（红色超时标注） |
| 4 | 折扣审批 恒信 12% | 1 重要 | 9 | 本周待办 |
| 5 | 请假审批 李四 | 0 普通 | 20 | 本周待办 |
| 6 | 目标确认 Q3 OKR 对齐 | 0 普通 | 40 | 知悉即可 |

> 上表即线框中的分组数（今天必须做 3 / 本周待办 2 / 知悉即可 1）。简报「① 合同审批 ② 采购审批 + 另有 1 件已超时（简历初筛）」对应前 3 条。

**重要性加分（用于「本周待办」组内排序，不改变上述主排序）**：满足任一加一档——关联金额 ≥ ¥50,000 / 我发起的流程被驳回 / 发起人为上级或关键客户关联人 / 该类型流程历史平均处理时长 > 24h。

**「我在等的事」判定**：我发起的流程实例停留 > 48h → 进入右栏 B4 并同时在简报收尾句提一句（「N 件你在等的流程还在走」）。

**输出（简报文案规则）**

- 结构固定四段：`问候 → 判断句 → ①② 逐项（是什么 + 谁 + 时限）→ 收尾句（其余 N 件）`。
- **必说 2–3 件**（第 1–3 优先级）：第 1、2 件用 ①② 逐项，第 3 件（若有）并句「另有 1 件今天到期」；其余折叠为「其余 N 件可以晚点看」。**上限 3 件**（超过 3 件就走「去待办中心」分流，不在简报里堆砌）。
- 文案风格约束：
  - 一件一句，先「是什么 + 谁」，后「时限」，最后可选「动作」（不写「请及时处理」这类空话）；
  - **不用形容词与模糊词**（禁止「建议」「可能」「大概」「重要的事」）；
  - 数字用阿拉伯数字；金额带 `¥` + 千分位；时间给「相对 + 绝对」双保险（「还剩 3 小时（15:00 前）」）；
  - 语气：同事口吻，简短，不卖萌，不寒暄超过一句；
  - **不复述全部待办**（清单是时间轴流的职责）；⛔ 禁止出现 DO 列表式罗列（「1. …2. …3. …」超过 2 条）。
- **诚实原则（强制）**：AI 不可用 / 超时 / 数据不足时，**不生成判断文案、不显示 `AI` 徽标**，降级为模板句简报（「你有 N 件事，最要紧的是 X（还剩 Y 小时）」）并附小字「AI 暂不可用，已按待办时限排序」。

### 5.2 意图流 + 智能填单（以「我要请假」为例）

| 阶段 | 设计 |
| --- | --- |
| **触发** | 点击意图流「我要请假」（PC 左栏 / 移动 B4 胶囊） |
| **载体** | PC：当前页轻抽屉（宽 480px，右侧滑入，不跳页）；移动：当前页全屏表单页（容器内导航栈推进，保留返回） |
| **表单来源** | 既有 `MOCK.workflow.formSchemas.leave_approval`（`leaveType` / `startTime` / `endTime` / `duration` / `reason`）——**不新建一套表单**，复用 `FormRenderer` / `wfRenderFormFill` 字段渲染内核 |
| **AI 预填规则** | ① `leaveType = 年假`（若剩余年假 > 0，否则不预填）；② `startTime = 下一个工作日 09:00`；③ `endTime = 次日 18:00`（默认 1 天）；④ `duration` 由起止时间计算（只读展示「1 天」）；⑤ `reason` **留空不编造** |
| **预填态视觉** | 预填字段：浅暖底 `#f6f5f4` + 字段右上角 `AI` 微徽标 + 下方小字「AI 已填，确认即可」；用户点击任意字符即切换为普通可编辑态（无二次确认，不阻碍修改） |
| **顶部说明条** | 表单顶部一行（28px 高，`#f6f5f4` 底）：「已根据你的剩余年假与日历预填 3 项，请确认后提交」+ 右侧「清空重填」文字按钮（回到全空表单） |
| **提交** | 底部主按钮「确认提交」（44px PC 38px）+ 次按钮「取消」；提交仍走 `formSchema` 必填双校验（前端 + 服务端，失败返回 `7008`） |
| **边界** | ① 拿不到剩余年假 → `leaveType` 不预填，字段旁标「需你填写」；② 不预填 `reason`、附件、金额类字段（**AI 不编造个人信息**）；③ 表单无 `formSchema`（外部流程）→ 意图项不出现「AI 已预填」标识，直接跳转；④ 用户修改预填值时，`AI` 徽标即时消失（明确「哪些是 AI 填的」） |
| **可复用性** | 「发起审批」「提个报销」共用同一套「预填 → 确认 → 提交」骨架；差异仅在预填字段规则表（按 `bizType` 配置，前端可配置化） |

### 5.3 AI 对话入口 / ⌘K 可识别指令

**四类指令与反馈方式**

| 类型 | 示例 | 识别后行为 | 反馈方式 |
| --- | --- | --- | --- |
| **导航类** | 「打开 CRM」「去待办」「看知识库」「应用中心」 | 直达目标（站内路由 / 外部新标签 SSO） | 面板关闭 + 页面跳转；无可跳转时提示「没找到匹配的应用，看看『全部应用』？」 |
| **查询类** | 「我还有几件事」「华宇的合同到哪了」「上周的报销」「谁在等我」 | **就地回答**（面板内返回结果卡片：标题 + 状态 + 时限 + 「查看全部 →」） | 结果卡片最多 5 条 + 摘要一句；不跳转，用户可继续追问 |
| **动作类** | 「发起请假」「提个报销」「催一下李四」「标记完成」 | ① 信息完整 → 直接拉起预填表单 / 执行；② 信息不全 → 追问 1 个必填槽位（不连续追问超过 2 轮） | 动作执行后 Toast；**写操作一律二次确认**（不可逆动作必须显式点「确认提交」） |
| **系统类** | 「切换角色」「退出登录」「自定义首页」「打开 AI 助手」 | 进入对应系统功能（编辑模式 / 角色切换 / 登出确认弹窗） | 沿用既有高危操作规范（登出为确认弹窗） |

**统一交互规则**

1. **就地优先**：能在面板/抽屉内回答的不跳转；必须跳转的，跳转前在面板内留一行说明（「已为你打开 CRM 合同列表」）。
2. **不空手而归**：无法识别时，返回 3 条最接近建议（按字符相似 + 业务类型命中排序），并提供「全部应用」「全部待办」兜底入口。
3. **AI 不自动执行写操作**：可发起（打开预填表单）但不可代提交；「标记完成」类动作需显式确认。
4. **可解释**：查询类结果的每一行附带一句「为什么给你这条」（如「今天 15:00 到期」），延续简报的「给判断」原则。
5. **示例（对齐 `MOCK` 数据，供原型照抄）**
   - 「我还有几件事」→ 「**6 件**待办：今天必须做 3 件（1 件已超时），本周 2 件，知悉 1 件」+ 3 条结果行 + 「全部待办 →」
   - 「华宇的合同到哪了」→ 「**华宇科技采购合同**（HT-2026-0918）在**法务审核**中，已在周律师处停留 **1h20m**；你有一条待办『合同审批 ¥120,000』**剩余 3h**」+ 「立即处理 →」
   - 「上周的报销」→ 命中 `MOCK.messages`：「报销单 BX-2026-0342 **已打款**（¥2,340，09-21 16:20），预计 1 个工作日到账」
   - 「催一下李四」→ 列出发起人/处理人为李四的可催办项 → 确认后调用催办（24h 去重）
6. **降级**：无网络时仅保留导航类与「最近」；面板/抽屉顶部一行小字「离线：仅支持本地操作」。
7. **PC 与移动共用同一识别内核**：PC 表现为 ⌘K 命令栏（快、不进入多轮对话）；移动表现为 AI 对话抽屉（可追问）；同一句「发起请假」在两端得到同一结果（同一预填规则）。

## 六、状态与边界设计

### 6.1 空态（0 条待办）—— 本设计要求的关键场景

| 区域 | 空态设计 |
| --- | --- |
| **今日简报（PC B1 / 移动 B1）** | 文案换为正向陈述：「今天没有必须处理的事。」+ 一句「N 条知悉类信息，3 件你在等的流程还在走。」；`AI` 徽标**保留**（这是判断，不是数据）；行动按钮换为「看看本月数据」（跳数据报表） |
| **时间轴流（PC B3 / 移动 B3）** | 不显示空白容器。替换为「本周已完成」正向反馈列表（最多 3 条，来自既有 `MOCK.todosDone`）+ 一行引导「今天可以发起点什么：〔提个报销〕〔发起审批〕」 |
| **意图流（PC B2 / 移动 B4）** | **空态下提升为主角**：默认展开全部 7 个意图项（PC）/ 全部胶囊（移动），标题从「我要做什么」改为「今天做点什么」。原因为：无待办时用户的目标从「处理」转为「发起」 |
| **右栏（PC B4/B5）** | 关注与动态：显示「没有在等的流程」一行 + 「看全部动态 →」；本月速览保留（有数据可看） |
| **全部区块均被隐藏（编辑模式极端情况）** | 该栏显示一条空栏提示：「本栏卡片已全部隐藏 · 进入编辑模式恢复 ▸」（可点击进编辑模式）；三栏均为空栏时，页面中部显示统一空态 + 「恢复默认模板」按钮 |

> **设计原则**：**空态不能是空白，必须换目标**。有活干 → 引导「处理」；没活干 → 引导「发起」或「了解」，绝不出现只有插图的空页面。

### 6.2 加载态 / AI 生成中态 / 网络异常态

| 状态 | 视觉与行为 |
| --- | --- |
| **常规加载** | 三块骨架屏：简报 3 行灰度条；意图流 6 个胶囊占位；时间轴流 4 行行骨架（行高按权重递减，避免加载完再跳变）。沿用 4.2「≤300ms 不显示 spinner，只显示骨架」 |
| **AI 简报生成中** | 简报卡内 `AI` 徽标后跟 12px 转圈；文案区显示「正在为你梳理今天的重点…」；随后逐句出现（每句 120ms，最多等待 **3s**） |
| **AI 简报超时/失败** | 3s 未返回 → 降级为模板句简报（见 §5.1 诚实原则），**移除 `AI` 徽标**，附小字「AI 暂不可用，已按待办时限排序」+ 「重试」文字按钮 |
| **网络异常** | 沿用既有 `.net-banner`（顶部红色横幅「⚠ 网络连接异常，部分数据可能不是最新」+ 关闭按钮）。同时：① 简报降级为「离线」态——**不显示 AI 判断文案**（判断依据可能过期，宁可不判断）；② 时间轴流显示**本地缓存的待办清单**并保留权重分组（缓存 ≤ 5 分钟以内才展示，超时则显示「数据可能过期」）；③ 意图流中外部系统项置灰 + tooltip「离线不可用」，站内意图（发起审批 / 我要请假 / 找人）**保持可用**（本地表单 + 本地主数据） |
| **单卡失败** | 沿用既有：该卡显示错误占位 + 「重试」，其他卡不受影响 |
| **会话过期** | 沿用既有：静默续期 → 失败弹窗跳登录（保留 redirect 回首页） |

### 6.3 数据量边界

| 待办条数 | 简报表现 | 时间轴流表现 | 移动端表现 |
| --- | --- | --- | --- |
| **0 条** | 见 §6.1 空态 | 换为「本周已完成」正向列表 | B2 大卡位换为「今天很清爽 ✓」卡 + 引导发起 |
| **1–5 条** | 必说 2（或 3）件，其余 0–3 件折叠 | 全部展开（今天必须做全展示，本周待办全展示，知悉即可折叠） | 大卡 + 其余全部列出 |
| **6–20 条** | 必说 2–3 件 + 「其余 N 件」折叠 | 今天必须做**全展示**；本周待办展示前 5 条 + 「还有 N 条本周待办 ▸」；知悉即可折叠（前 2 条 + 计数） | 大卡 + 其余展示前 4 条 + 「查看全部 N 条 →」 |
| **21–50 条** | 必说 3 件 + 分组计数（「其余 3 件本周、12 件知悉」） | **渲染上限 20 条**：今天必须做（≤10 全展示）→ 本周待办（前 5）→ 知悉即可（折叠计数）；底部「查看全部 N 条 →」 | 其余展示前 4 条 + 「查看全部」；大卡固定为第 1 优先项 |
| **> 50 条** | 同上，并追加警示行「你的待办较多（N 条），建议先处理超时项」+ 「去待办中心筛选 →」（引导分流，而非在首页堆砌） | | |
| **超长文本** | 简报中标题 > 24 字截断为「…」并在展开列表完整展示 | 行标题 1 行省略（`text-overflow: ellipsis`），`title` 属性给全文 | 标题 2 行省略 |

> **性能边界**：首页总渲染行项目 ≤ 20；简报文案 ≤ 4 句；意图项固定 ≤ 8 行（7 动作 + 1 次级入口）；右栏动态 ≤ 5。首页首屏**不做全量渲染**，其余一律「查看全部」分流。
