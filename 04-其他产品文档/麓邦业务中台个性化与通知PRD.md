## 一、文档定位与现状回顾

### 1.1 本次是增量，不是新建

本 PRD 是**增量需求**：不新建页面、不新建模块、不新建一套布局系统。四组需求全部落在**既有页面与既有数据模型之上**，其中：

## 二、需求一：千人千面（AI 智能推荐排序）

> 编号：**A1-F05**（门户域 A1，顶层序号 A1-F05 未被占用）

### 2.1 产品定义

**「千人千面」= 系统按使用者本人的真实行为，自动调整首页的「呈现顺序与推荐」，无需任何人人工配置。**

必须与既有能力划清边界：

| 能力 | 是什么 | 谁决定 | 现状 |
| --- | --- | --- | --- |
| **角色模板**（既有，A1-F02） | 同一角色的人看到的**卡片集合与默认布局相同** | 管理员在 UI-C-11 配置 | 已有 |
| **个人微调**（既有，决议 #6） | 用户**手动**调卡片显隐/顺序/栏宽 | 用户手动 | 已有 |
| **千人千面**（本次，A1-F05） | 在**不改结构、不越权限**的前提下，按用户行为**自动**决定「应用先看到谁、推荐什么、同类待办谁靠前」 | 系统自动（AI/规则） | **本次新增** |

**一句话口径**：角色模板与个人微调决定「**你看到哪些卡片**」；千人千面决定「**卡片里的东西谁在前、推荐什么**」。

### 2.2 输入信号清单（每项标注数据来源与现状）

| # | 信号 | 说明 | 数据来源 | 现状判定 |
| --- | --- | --- | --- | --- |
| S1 | **应用打开频次** | 近 30 天应用被点击次数（带时间衰减） | `MOCK.apps[].freq`（静态值）；正式需改由埋点累计 | **既有字段，但为静态值** → 需接真实埋点 |
| S2 | **应用打开时段分布** | 打开时间落在「周一上午 / 工作日 9–11 点 / 月末」等时段的占比，用于生成「你每周一上午都会打开它」类理由 | **不存在**；需新增埋点事件 `app_open`（上报 `appId` + `ts`） | **需新增采集** |
| S3 | **待办处理习惯** | 用户「提前处理」还是「临近时限才处理」；平均停留时长 | 数据模型基础已有（`MOCK.todos[].urgency / remainHours / overdue / time`）；**处理行为需新增埋点** `todo_handle`（处理动作 + 处理时刻 + 时限剩余） | **部分既有 / 部分新增** |
| S4 | **待办来源与类型偏好** | 常处理的来源系统（CRM / OA / 招聘系统 / 目标管理）与业务类型（`contract_approval` / `leave_approval` / `resume_screen` …） | 既有 `MOCK.todos[].source` + `bizType`；`MOCK.workflow.approvalCenter` 同构 | **既有** |
| S5 | **意图流使用分布** | 各意图项（发起审批 / 我要请假 / 找人 …）的点击次数 | **不存在**；`home-v2.html` 的 `INTENTS` 为前端静态配置数组；需新增埋点 `intent_click` | **需新增采集** |
| S6 | **常访问内容类型** | 消息分类点击分布（公告 / 审批结果 / 系统通知 / 待办提醒） | 既有分类字段 `MOCK.messages[].cat`；**点击行为需新增埋点** | **部分既有 / 部分新增** |
| S7 | **角色 / 组织 / 岗位**（**冷启动兜底**，非排序信号） | 无行为数据时的默认排序依据 | 既有 `MOCK.user.roles`、`MOCK.employees[].org/post`、`MOCK.layoutTemplate` / `layoutTemplateV2`（角色模板） | **既有** |
| S8 | **权限范围**（**硬约束，非排序信号**） | 可推荐集合 = 用户**有权访问**的应用与内容 | 既有 `MOCK.permTree`（菜单/按钮/接口权限点）+ `MOCK.roles`；接口 `POST /perm/check`（B2-F05） | **既有** |

> **信号使用原则（写入技术约束）**：S1–S6 只用于**排序**；S7 只用于**冷启动兜底**；S8 是**前置过滤**（先权限、后排序），**绝不作为排序特征**。

### 2.3 输出效果（逐项说明「变什么 / 不变什么」）

| 输出项 | **变什么** | **不变什么** |
| --- | --- | --- |
| **应用排序自适应** | 「全部应用」（`all-apps` 区块）与「AI 为你推荐」区内的**顺序**按 S1–S3 重排，高频/当列宁舍的应用前置（示例：`CRM 客户管理` freq 32 → 首位） | 应用**集合**、分组（业务系统 / 协作平台）、图标、名称、SSO 跳转方式；**无权限应用依然不出现** |
| **「AI 为你推荐」区** | 首页新增 `ai-recommend` 区块：3 张推荐卡（图标 + 名称 + **推荐理由** + 「立即打开 →」），随信号更新 | 卡片集合不因推荐而增删；推荐区本身可被用户在编辑模式隐藏（决议 #6）；推荐理由模板沿用 `sample-notion.html` 既有文案风格（如「你每周一上午都会打开它，已连续 12 周」） |
| **时间轴流权重微调** | 同组内的**行顺序**可按 S4（用户常处理的 `bizType` / 来源）适度加权 | ① 分组阈值（today / week / know）不变；② 视觉权重表（行高 / 字号 / 色条 / 操作形态）不变；③ 行项目结构不变；④ **AI 不得把低紧迫度项提到高紧迫度项之前**（跨组不动） |
| **AI 简报措辞** | 简报可引用用户习惯（如「你通常在上午处理合同审批」）作为收尾句补充 | 简报四段结构、必说 2–3 件上限、诚实原则（AI 不可用即降级模板句、移除 AI 徽标）均不变 |
| **首页结构** | 不变 | 三栏结构（左栏 + 中栏 + 右栏）、区块包裹层级、编辑模式、布局引擎机制全部不变 |

### 2.4 硬边界（五条，必须写清并逐条验收）

| # | 硬边界 | 具体约束 | 违反时的判定 |
| --- | --- | --- | --- |
| **H1** | **AI 只调顺序，不改结构** | 只允许改 `order` 语义上的**呈现顺序**与推荐区内容；**不得**增删卡片、不得改三栏结构、不得改 `layoutTemplate` 的 `cards` 集合 | 若首页出现「因推荐而多出/少了一个区块」→ 判失败 |
| **H2** | **无权限内容绝不推荐（权限优先于推荐）** | 排序前先做权限过滤：可推荐集合 = `permTree` 校验通过的应用/内容；推荐区、应用排序、内容推荐**均只能在该集合内进行**。**不允许出现"推荐了但点不开"** | 用无 CRM 权限账号走查：CRM 既不出现在排序结果，也不出现在推荐区 |
| **H3** | **可关闭（回到固定排序）** | 个人设置提供开关「智能排序」（`ai_rank_enabled`）；关闭后首页回到**固定排序** = 角色模板 `order` 为第一依据 + `freq` 降序为第二依据；关闭动作即时生效，无需刷新 | 关闭后仍按 AI 顺序呈现 → 判失败 |
| **H4** | **可解释（推荐须给理由）** | 每一条推荐、每一次「顺序异常前置」都必须能给出**来自真实信号**的理由文案（如「你每周一上午都会打开它，已连续 12 周」「检测到你有 3 笔待填报销草稿」）。**禁止编造理由**；无法给出理由时不得前置、不得推荐 | 推荐卡无理由文案，或理由与信号不符 → 判失败 |
| **H5** | **冷启动退化（不假装有推荐）** | 新用户/行为数据不足（阈值：有效行为事件 < 20 条 或 使用时长短于 7 天）时：① 应用排序退化为**角色模板默认排序 + `freq` 降序**；② 推荐区**不展示 AI 徽标**（或整体隐藏），**不展示任何"猜测式"推荐**；③ 简报不引用习惯 | 无数据时仍显示「AI 为你推荐」并给出貌似个性化的理由 → 判失败（属欺骗性设计） |

### 2.6 验收标准（可演示、可验证）

| 验收项 | 验证方式 | 通过标准 |
| --- | --- | --- |
| **AI 排序 vs 固定排序** | 原型提供「对比演示」入口：同一首页上并排/切换展示两种排序结果 | 肉眼可见首位应用不同；差异原因可点开查看（对应信号） |
| **推荐有理由** | 逐条查看推荐卡的推荐理由 | 每条推荐均有理由；理由与信号一致，无编造 |
| **可关闭** | 个人设置关闭「智能排序」→ 返回首页 | 首页立刻回到固定排序；无残留 AI 标识 |
| **不越权限** | 用无 CRM 权限账号登录 | CRM 不出现在排序结果与推荐区（0 次出现） |
| **冷启动退化** | 用无行为数据的新账号登录 | 按角色模板默认排序；推荐区隐藏；无 AI 徽标 |
| **不改结构** | 开启/关闭 AI 排序前后对比首页区块清单 | 区块清单（cardId 集合）完全一致；仅区块内内容顺序变化 |

## 三、需求二：个人界面风格定制（轻定制）

> 编号：**A1-F06**（门户域 A1，顶层序号 A1-F06 未被占用）

### 3.1 产品定义

在既有「首页个性化」（**布局**定制）之外，新增「**界面风格**」（**视觉**定制）。轻定制的含义是：**只开三把旋钮（主题色 / 内容密度 / 圆角），不做主题市场、不做自定义上传、不做暗色。**

### 3.2 三个维度的选项清单与取值

#### 3.2.1 主题色（1 个默认 + 4 个预设）

| 档位 | 色值 | 说明 | 影响范围 |
| --- | --- | --- | --- |
| **麓邦红（默认）** | `#C8161D` | 品牌色，与既有 `--bmp-color-primary` 一致 | 主操作按钮、链接、导航选中态、激活态、焦点环 |
| 靛蓝 | `#2F6FEB` | 冷调补充色，与暖白底对比舒适 | 同上 |
| 石墨灰 | `#4A4A47` | 与暖色中性系（`#31302e` / `#615d59`）同族，最"安静"的选项 | 同上 |
| 暖橙 | `#DD5B00` | 直接复用既有 `--bmp-color-accent-warm`（已在首页用于"本周待办"色条） | 同上 |
| 青竹绿 | `#1F7A5A` | 低饱和绿，避让语义绿（`#16A34A` 成功色）明度与饱和度 | 同上 |

**派生规则（必须成对定义，否则会出现"只有按钮变色、链接没变"）**：每个主题色需同时给出 `primary` / `primary-light`（8% 淡化，用于 hover 底、选中标签底）/ `primary-dark`（加深 15%，用于按钮 hover/active）三档。

**主题色不改变什么（硬规则）**：

- **语义色固定，永不随主题色改变**：`success #16A34A`、`warning #F59E0B`、`danger #F53F3F`、`info #64748B`。
- **紧急 / 超时语义红固定为 `#C8161D`**。理由：按 §9.2 Token 升级规则修订第 1 条，"紧急/超时/临期"语义统一由品牌红承担。**若用户把主题色改为靛蓝，主按钮变蓝，但"紧急"圆点与"已超时"文字仍必须是红色**——否则会出现"红色的东西不再是警示"，这是不可接受的安全/认知风险。
- 渠道品牌色（钉钉 `#1677FF`、企微 `#07C160`）不变。

#### 3.2.2 内容密度（三档）

| 档位 | 行高 | 卡片内边距 | 区块间距 | 表格行高 | 适用场景 |
| --- | --- | --- | --- | --- | --- |
| 宽松 | 1.7 | 20px | 20px | 52px | 喜欢留白、单屏信息少的用户 |
| **标准（默认）** | 1.5 | 16px | 16px | 44px | 与既有规范一致（4px 基准阶梯，卡内 16px，区块 16px） |
| 紧凑 | 1.35 | 12px | 12px | 36px | 信息密集型用户（如需要一屏看完全部待办的人） |

**影响的属性（须落在 Token 层，不得逐页硬编码）**：`--bmp-density-line-height`、`--bmp-space-card`、`--bmp-space-block`、`--bmp-row-h`。
**不影响的属性**：字号档位（h1/h2/body/caption 一律不变）、栅格数、栏宽、图片与图标尺寸。理由：字号一起变会让"密度"退化为"缩放"，破坏排版系统。

#### 3.2.3 圆角（三档）

| 档位 | `--bmp-radius-sm`（按钮 / 输入框） | `--bmp-radius-md`（卡片 / 面板） | `--bmp-radius-lg`（弹窗 / 抽屉） |
| --- | --- | --- | --- |
| 直角 | 4px | 4px | 6px |
| **标准（默认）** | 4px | 8px | 12px |
| 圆润 | 6px | 12px | 16px |

`--bmp-radius-pill`（9999px：徽标、标签、胶囊、头像）**三档均不变**——胶囊形态一旦受影响会出现"药丸变圆角矩形"的形态错乱。

### 3.3 硬边界（四条）

| # | 硬边界 | 具体约束 | 理由 |
| --- | --- | --- | --- |
| **H1** | **不做暗色模式** | 本次不提供暗色主题，也不预留暗色入口 | 守 UIUX 决议 #3（"仅提供浅色主题，不做暗色模式，V1.5 也不列入"）。理由见 6.1 |
| **H2** | **语义色不随主题色改变** | 成功 / 警告 / 错误 / **紧急**四类语义色固定，包含提醒、警示、危险按钮一律不随主题色变化 | 避免"红色不再警示"——若紧急与错误都随主题变色，用户将失去跨页面稳定的危险信号；这是安全与认知一致性问题，不是审美问题 |
| **H3** | **不改变布局与功能，只改视觉 Token** | 不改卡片显隐、顺序、栏宽、栅格；不改任何交互流程与功能可用性 | 布局属决议 #6 的既有能力（个人微调 + 角色模板），风格定制不得越界 |
| **H4** | **全部落在 `--bmp-*` Token 层** | 三档全部通过 CSS 变量注入（`html[data-theme]` / `data-density` / `data-radius`），组件内**禁止**硬编码色值与半径 | 既有约定"全部走 CSS 变量，未来可扩展；色彩全走 Token，未来如需暗色只扩 Token 层"（决议 #3） |

两者是**「布局定制」与「视觉定制」的分工**，落在同一设置页的不同 Tab：

## 四、需求三：通知 Banner + 后台管理

> 前台编号：**A1-F07**（新增）｜后台编号：**A1-F04-1 ~ A1-F04-4**（既有 A1-F04 公告管理的**子编号**，不改变 A1-F04 含义）

### 4.1 前台展示规则

#### 4.1.1 位置（PC + 移动）

| 端 | 位置（精确到插入点） | 是否吸顶 |
| --- | --- | --- |
| **PC**（`home-v2.html`） | 顶栏（`.topbar`，56px sticky）**之下**、网络异常横幅（`.net-banner`）**之上**、三栏内容区（`main.hw`）**之前** | **不吸顶**：随页面滚动一起滚走。理由：首页首屏已承载"最要紧的一件事"（首页重构规格的"三秒检验"），banner 长期吸顶会持续挤压首屏最高价值位 |
| **移动**（`mobile/home-v2.html`） | 钉钉容器导航栏（44px）**之下**、内容容器 `.m-wrap` **之前**（随内容滚动） | 不吸顶。理由同上，移动端首屏更稀缺（375px 宽） |

#### 4.1.2 显隐条件（**本需求最硬的一条**）

> **有「已发布 且 未过期 且 开启了 Banner 展示」的公告 → 显示；无 → 完全不占位。**

| 判定项 | 规则 |
| --- | --- |
| 已发布 | 公告状态为「已发布」（非草稿、非已撤回） |
| 开启了 Banner 展示 | `bannerEnabled = true`（后台开关，见 4.3） |
| 未过期 | 当前时间 ∈ [`bannerStartTime`, `bannerEndTime`]；未配置时段时默认「发布时间 → 无终期」 |
| 未关闭 | 不在当前用户的「已关闭公告 id」列表中 |
| **无匹配项时** | **不渲染 banner 节点**（不是 `display:none`，而是**不插入 DOM**）。页面高度为 0、无边框、无底色、无占位留白 |

#### 4.1.3 内容构成

| 元素 | 规格说明 |
| --- | --- |
| **类型标签** | 通知 / 新闻 / 紧急 三选一（胶囊形态，沿用 `--bmp-radius-pill`）。语义色：通知=中性、新闻=主色、**紧急=危险红**（此处"紧急"用语义红，不随主题色改变，与 3.2.1 硬规则一致） |
| 标题 | 公告标题，单行省略（`text-overflow: ellipsis`），`title` 属性给全文 |
| 摘要 | 一句摘要，≤40 字，超出省略（后台可填，未填时取正文首句） |
| 发布时间 | 列表内相对时间（如「2 小时前」）+ hover 显示绝对时间（沿用既有 4.4 时间显示规范） |
| 操作 | 「查看详情」→ 跳公告详情（PC 使用既有详情抽屉范式；移动为容器内导航栈推进） |
| 关闭 | 右侧 `✕` 关闭按钮 |

#### 4.1.4 多条时的轮播规则

| 条数 | 行为 |
| --- | --- |
| 0 条 | 不占位（见 4.1.2） |
| 1 条 | 静态展示，**不轮播**，不显示指示器与左右按钮 |
| ≥2 条 | 轮播：每 **6 秒**自动切换；鼠标 hover 暂停（移动端触摸时暂停）；提供「1 / N」指示器与左右切换按钮；切换动效 ≤200ms ease-out（遵守既有动效规范）；**尊重系统「减少动态效果」**——开启时改为手动切换 |

**展示顺序（固定优先级链）**：
`top = true`（置顶，复用既有 `MOCK.notices[].top` 字段）→ `bannerPriority` 降序 → 发布时间降序。
> 说明：置顶字段 `top` 在既有数据与后台上已存在（`pages-config.js` 中 `notices-admin` 已用 `r.top` 渲染「📢 / 已置顶」标签），本次**直接复用，不新增置顶概念**。

#### 4.1.5 可关闭规则

| 规则 | 说明 |
| --- | --- |
| 关闭粒度 | **按公告 id 关闭**（不是关闭整个 banner） |
| 记录载体 | 原型：`localStorage: bmp_banner_closed`（id 数组）；正式：`user_preference.banner_closed` |
| 效果 | 该公告不再向该用户展示；若因此无剩余公告 → **banner 整体收起，完全不占位** |
| 关闭最后一条后的位置 | 剩余区域自然上移，不留空隙 |
| 例外（待确认） | 「紧急」类型是否允许关闭 → 建议**不可关闭**（安全/合规通告不应被屏蔽），见待确认 Q1 |

### 4.2 与既有消息/公告的关系（避免重复展示）

| 区域 | 承担什么 | 说明 |
| --- | --- | --- |
| 首页 Banner（本次，A1-F07） | **只承担"公司级、需要一眼看到"的公告**（由后台逐条开启） | 内容少而精，条数由后台控制 |
| 右栏「关注与动态」（既有，首页重构规格 B4） | 置顶公告、系统维护通知、审批结果等**阅读类信息流** | 与 Banner 语义不同：一个是"喊一声"，一个是"可以慢慢看" |
| 消息中心（既有，A1-F03） | 全量消息归档与已读管理 | 完整落点 |
| 时间轴流（既有，B3） | **不含公告/消息**（只放待办性质的知悉项，既有分工说明） | 本次不改变此分工 |

**去重规则**：同一公告若已在 Banner 展示，右栏动态中**仍可出现**（阅读流与通知条语义不同，不做互斥）；但 **Banner 内部不得重复**（同一公告 id 只出现一次）。

### 4.3 后台管理增强（在既有「公告管理」上扩展）

**落点**：既有后台页「门户运营 → 公告管理」（`pages-config.js` 中 `PAGES["notices-admin"]`，UI-C-12）。

**新增字段清单（建议）**：

| 字段 | 含义 | 取值 |

| `type` | 公告类型 | `notice` 通知 / `news` 新闻 / `urgent` 紧急 |

**后台新增能力**：

| 能力 | 说明 |
| --- | --- |
| 「是否在 Banner 展示」开关 | 列表行内可快速切换，或编辑弹窗内开关；切换写审计（E2） |
| 「Banner 展示时段」 | 起止时间选择器；校验「起 < 止」；期间外 banner 不展示（但公告本身在消息中心仍可见） |

| 撤回联动 | 撤回公告 → banner **立即消失**（撤回既有高危确认流程不变，仅补充"同时从首页 Banner 移除"的提示文案） |

## 六、与既有决议 / 文档的关系

### 6.1 决议 #3（不做暗色）冲突处理

| 项 | 结论 |
| --- | --- |
| 本次是否做暗色 | **不做，维持决议 #3**（"仅提供浅色主题，不做暗色模式，V1.5 也不列入"） |
| 不做暗色的理由 | ① **与既有决议直接冲突**，本次为增量 PRD，无权改写决议；② 暗色需为全站 30 页 × L0/L1/L2 组件出第二套 Token 并逐页走查，成本远超"轻定制"的定位；③ 现有暖色体系（暖白 + 细边框 + 低透明度阴影）在暗色下需重新设计（不是反色即可）；④ 企业办公场景以日间使用为主 |
| 未来若要做 | **需另立需求**：独立增量 PRD + UIUX 增量章节 + 决议更新，并重做对比度与红色职责走查。**本次不预留暗色入口、不做暗色预览**（避免出现"半成品暗色"） |
| 与"色彩全走 Token"的关系 | 本次三条旋钮全部落在 `--bmp-*` Token 层（H4），因此**未来若真要做暗色，只需扩 Token 层**——本次工作不会成为暗色的障碍，这一点在文档中明确记录 |

### 6.2 决议 #6 的关系：个性化从「布局微调」扩展为「布局 + 视觉 + 排序」

| 维度 | 载体 | 谁是决策者 | 状态 |
| --- | --- | --- | --- |
| **布局**（卡片显隐 / 栏内顺序 / 栏内栅格） | `user_override_json` → `layout_override` | 用户手动 | 既有（决议 #6），**本次不改** |
| **视觉**（主题色 / 内容密度 / 圆角） | `bmp_ui_style` → `ui_style_json` | 用户手动 | **本次新增（A1-F06）** |
| **内容排序**（AI 智能推荐排序） | `ai_rank_enabled` + 服务端排序结果 | 系统自动（用户可关） | **本次新增（A1-F05）** |
| **卡片集合** | 角色模板 `template_json` | 管理员（UI-C-11） | 既有，**本次仍不放开**（硬约束保持） |

**关键点**：决议 #6 的核心约束是「**cardId 集合不可增删**」。本次 A1-F05 新增的 `ai-recommend` 是**注册进 `cardManifest` 的新卡片**（走既有"新卡片 = 注册 manifest + 发布组件，零平台改造"机制），**不是让 AI 动态增删卡片**——这与决议 #6 **不冲突**：AI 只决定"卡片里的顺序与推荐内容"，卡片的存在与否仍由角色模板决定。
